# Click-Clean 2.3 内存整理有效性复核与实施建议

日期：2026-10-03。按用户要求由 Astra 独立审计。范围为 `Core/MemoryEngine.cs`、`WindowsMemoryApi.cs`、`AutomationPolicy.cs`、`Store.cs`、`DockStatus.cs`、`App/MainWindow.xaml.cs` / `.xaml`、`Tests/Program.cs` 和上一轮 `docs/memory-review-astra.md`。本报告描述审查时的基线及建议，不代表建议已经实现；最终实现与验证以本轮主代理交付为准。

本轮只读源码并查阅主来源，没有执行真实整理、读取用户历史、运行压力实验或改变用户设置。上一轮匿名历史数字没有在本轮重新验证，不用它证明效果。没有引入或复制 PCL 代码，也不改变项目现有 GPL 来源与归属。

## 核心判断

最需要优化的是“何时不执行”和“如何说明结果”。目前没有证据证明三步全系统整理能持续提高应用性能。可用内存增加仅是内存状态变化，不能当成释放应用分配、修复泄漏或提速证明。公开 API 也不能兑现普遍、安全的全系统提速承诺。

尤其不能把“更多空闲”作为唯一目标：当前 `Available` 已经包含可立即复用的待机缓存。清待机主要改变可用池内部构成，而触发器使用的是 `100 × (Total − Available) / Total`。因此“使用率高 → 清待机 → 期望使用率降低”存在指标与动作错配。这是根据代码和微软定义作出的推断，并非所有负载的实测结论。[微软 MEMORYSTATUSEX](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/ns-sysinfoapi-memorystatusex)

## 已验证的基线

- `MemoryCommand` 为 2/3/4；`Execute` 调用 `NtSetSystemInformation(80, ...)`；引擎去重后按编号执行，遇失败停止，最终恢复临时权限。取消不能中止正在进行的系统调用。
- 新用户 `SelectedSteps` 默认三步，空值或全无效也回填三步。主按钮、托盘和底部岛独立硬编码三步，只有“整理所选项目”使用选择值。仅改设置默认值不能修正全部入口。
- 自动默认关闭；启用后 `FullCleanup=false` 只清待机，`true` 执行三步。阈值持续时间、冷却、迟滞、并发拦截、休眠断档、连续失败暂停已存在；定时触发本身不要求高压力。
- `AvailableChange` 已保留正值、零和负值，已有对应 FakeApi 测试。UI 已注明其他程序活动影响。这些是应保留的优点。
- 只读取立即结束快照，没有延迟复测。`CleanupResult.Success` 同时依赖步骤状态和观测异常，故“系统调用已完成，但后快照失败”会进入失败/部分完成展示，不能单从该布尔值解释底层调用结果。
- 现有 `PerformanceInformation` 已声明 `SystemCache`、`KernelPaged`、`KernelNonpaged`，但没有投射进 `MemorySnapshot`；无需发明内部结构即可逐步增加诊断指标。

## 三步各自能做什么

| 步骤 | 机制与局限 | 不应承诺的效果 |
| --- | --- | --- |
| 2：裁剪工作集 | 将可分页驻留页移出工作集；再次访问可能软缺页，也可能需要从后备存储读回 | 没有释放应用持有的全部分配，不等于减少提交量或解决泄漏 |
| 3：刷新修改页 | 脏的过渡页重新利用前需要写回；主动推动这一过程可能造成 I/O 竞争 | 不能将可用量差值当成实际刷盘量，不能保证减少总写入 |
| 4：清待机 | 丢弃可复用的干净缓存，可能导致后续重新读取 | 待机已计入 Available；不保证降低本软件使用率，更不保证任务更快 |

微软说明工作集只包含可分页驻留页，过渡页可继续留在 RAM，软缺页不必访问磁盘，脏页重新利用前需要写入后备存储。因此不能把所有裁剪都描述成立即换出到磁盘，也不能把“API 成功”解释为净收益。[微软 Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)

编号与 Native 枚举对应关系由 System Informer 的原始 `phnt` 声明交叉验证：信息类 80，以及 `MemoryEmptyWorkingSets`、`MemoryFlushModifiedList`、`MemoryPurgeStandbyList`。该来源把相关结构/枚举标为 `private`；它是项目原始声明，不是微软公开稳定支持承诺。不能据此宣称所有 Windows 版本兼容，也不建议本轮再引入更多未公开结构来“精确优化”。[phnt 原始声明](https://raw.githubusercontent.com/winsiderss/phnt/master/ntexapi.h)

## 本轮建议：减少干预，保留既有功能目标

用户已有阈值及定时清理需求。把自动清理直接改成仅提醒，属于明显行为变化，必须告知并提供选择，不能冒充内部优化悄然替换。以下是可落实的低风险组合；是否全部采用由本轮实现决定。

1. **统一入口决策。** 主按钮、托盘、底部岛共同进入同一压力检查。低于产品阈值、快照无效或未知时真正跳过：不启用权限、不调用 Native API、不制造成功整理。高使用率只是触发启发式，不代表存在可安全清理的目标。阈值应标为产品策略，不能描述为 Windows 官方健康界限。
2. **将全系统激进步骤放在明确的手动高级入口。** 用户逐项选择后可以强制执行，并说明可能发生缺页、刷盘和缓存重建。新用户不要默认三步全选；空选择应保持空，不能由 `Store.Validate` 恢复为三步。旧选择可保留在高级界面，不能自动等同于新快捷策略的授权。
3. **自动仍保留阈值/定时开关，默认关闭。** 对 standby-only 自动尝试增加最新压力检查：定时到期但压力不足也跳过。不要自动升级为工作集裁剪或刷新修改页。文案必须直说“清理待机缓存，可能不降低使用率；未证明提速”。这会减少无必要操作，但不能解决待机动作本身与 Load 错配的根本问题。
4. **处理旧 FullCleanup 要显式迁移。** 建议保留旧值以识别历史选择，向用户展示“继续使用待机自动 / 关闭自动 / 前往手动高级”的选择；决定前暂停旧全量自动策略并清楚说明原因。该暂停同样是行为变化，不能藏在普通保存里。如果本轮不能完成迁移交互，可暂时保留旧显式全量选择并明确标为高级兼容策略，不能同时宣称“自动模式绝不执行全量”。不应无提示强制清掉旧值，也不应把旧勾选视为任何新动作的通用授权。
5. **跳过独立于失败。** 跳过不计连续自动失败，不更新“上次真实整理”，不累计释放量。自动周期应正常推进/进入适当观察间隔，避免低压力每次采样都重新尝试。错误、用户取消、观察未完成也应分别展示。
6. **高级执行保留现有防线。** 仍按稳定顺序去重、禁止并发、失败即停、恢复权限。未知系统返回码如实报告，不尝试驱动绕过、杀软排除或硬件配置修改。

如果产品希望保留“点击立刻做点什么”，在压力足够时只清待机是较少步骤的兼容方案；它不能被命名成已验证有效的“智能提速”。更诚实的长期方向是把压力监测、占用来源诊断和有证据的针对性处理作为主要价值。

## 观测：即时值与复测值都保留

建议在当前即时快照之外，增加例如 3 秒后的异步复测；3 秒是初始产品参数，不是能证明收益的科学窗口。记录实际间隔，并显示两组相对整理前的有符号差值，同时显示提交量变化。禁止截掉负数、只取两者最大值或把绝对值显示为释放量。

- 先完成系统调用并恢复权限，再等待复测；保持运行门闩直到观察结束，防止另一次整理混入本次窗口。UI 可以保持响应。
- 等待阶段取消只跳过剩余观测，不把已执行成功的调用改称撤销或失败；退出也应能取消观察。
- 复测读取失败属于观测不可用，保留即时快照和每一步状态。新增可空字段应兼容旧历史，缺测不能反序列化成 0 或伪造 3 秒观测。
- 将“步骤执行结果”“观测是否完整”“内存变化”分开。零变化可显示 `0.00 GiB`；负变化照实显示；都不等于 API 调用失败。短期回落只说明观测到回落，不能归因于软件无效或程序泄漏。

微软明确 `GlobalMemoryStatusEx` 数据会变化，连续调用也不保证相同。前后快照没有隔离其他进程，两次 API 读取也不是原子事务。复测提高可见性，但不能消除混杂，不能证明性能改善或持续收益。[微软 GlobalMemoryStatusEx](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-globalmemorystatusex)

## 可观测性的后续选择

可以使用已有 `GetPerformanceInfo` 字段展示系统缓存、内核分页池/非分页池、提交压力。每个页数乘 `PageSize` 时保留溢出检查。特别注意微软定义的 `SystemCache` 是**待机列表加系统工作集**，不能把它标成纯待机，也不能与 Available 相减臆算修改页。提交接近上限可以提示压力，但工作集裁剪不会自动解除应用的提交承诺。[微软 PERFORMANCE_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-performance_information)

还可采用公开的 `CreateMemoryResourceNotification(LowMemoryResourceNotification)` 和非阻塞的 `QueryMemoryResourceNotification` 增加操作系统低内存信号。应复用并关闭句柄，失败保留“未知”；未收到低内存通知不等于高内存充足，因为微软说明两者之间存在都不触发的区间。该机制用于应用按系统压力调整用量，不能推导出第三方全系统裁剪必然有益。[创建通知](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-creatememoryresourcenotification)、[查询通知](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-querymemoryresourcenotification)

没有纯待机数量时，不应伪造“可回收缓存”或收益门槛。自动只提醒是可以提供的后续选项，但不是本轮在用户不知情时必须进行的替换。公开 `EmptyWorkingSet` 能指定进程，却仍是裁剪驻留页；全进程枚举并逐个调用也不是安全提速替代品。若未来做针对性处理，须由用户明确选择目标并实测其恢复代价。[微软 EmptyWorkingSet](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-emptyworkingset)

## 本轮建议测试矩阵

以下主要使用 FakeApi、假时钟和独立临时存储，不需要真实整理或压力测试。

| 场景 | 必须验证 |
| --- | --- |
| 快捷入口一致性 | 主按钮、托盘、底部岛使用同一策略，不再漏出硬编码三步 |
| 正常/未知压力 | 返回明确跳过；特权与 Execute 调用次数均为零；不显示释放成功 |
| 高压力与定时 | 持续、冷却、迟滞仍有效；定时低压力跳过不积压；自动不意外升级动作 |
| 高级手动 | 显式组合、去重、顺序、失败停止；强制执行仍受运行锁约束 |
| 设置迁移 | 新默认、空数组、无效枚举、旧三步、旧 FullCleanup 各有明确处理；不能静默回填三步 |
| 零/负/短期回落 | 即时与复测差值原样保存；不使用最大值，不把 API 成功说成性能改善 |
| 观测异常 | 即时失败、复测失败、缺测旧历史都保持未知；不伪造数值，不丢步骤状态 |
| 复测取消和并发 | 调用中取消只影响后续；观察中取消只终止观察；观察期间再次点击不混入结果 |
| 跳过与失败计数 | 跳过不计失败、不更新真实整理时间；真实连续失败仍暂停 |
| 历史往返 | 新字段可空，实际观察间隔有效，旧记录仍可读，零和负值往返不变 |

性能有效性仍需另外测量：在相同工作负载下对照不操作、单步及组合，观察后续任务耗时/交互延迟、缺页、磁盘活动以及可用量和提交量。游戏应看帧时间尾部。要控制缓存冷热和运行顺序；单次“多了几 GiB”不足以选择最优策略。本报告没有进行这些实验，也没有给出尚不存在的提升百分比。
