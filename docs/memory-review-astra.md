# Click-Clean 内存整理独立评估

评估日期：2026-10-02。应用户要求，由 `gpt-6-astra` 独立只读审查当前实现、匿名汇总本机历史并核查主来源。本轮没有为评估执行真实整理。结论经主代理核对代码与微软文档；不是硬件安全认证，也不是性能保证。

## 结论

当前整理确实改变内存驻留状态，能暂时增加可用内存，但没有证据证明稳定提速。未发现直接损伤 RAM、CPU 的代码机制；主要风险是缺页、磁盘读写和响应波动。SSD 可能承受额外累计写入，无法从可用内存差值推算磨损量。提升方向应是减少无益干预、验证实际性能收益和定位占用来源，而非单纯追求更低百分比。

## 当前实现与作用范围

`Core/WindowsMemoryApi.cs` 启用 `SeProfileSingleProcessPrivilege`，调用 `NtSetSystemInformation(80, command)`。`MemoryEngine` 对选择去重并按 2→3→4 排序，逐步检查返回码，失败停止后续步骤，结束恢复权限。取消只阻止未开始的步骤，不中断当前系统调用。手动默认三步全选，自动默认关闭；自动启用后的默认动作仅清待机。

| 命令 | 实际作用 | 代价与边界 |
| --- | --- | --- |
| 2：裁剪全系统工作集 | 将可分页驻留页移出工作集；不等于释放应用持有的内存分配 | 再次访问可能发生软缺页或需磁盘读回的硬缺页 |
| 3：刷新修改页 | 推动脏页写入后备存储，使页面可以重新利用 | 增加当时的磁盘写入与竞争；部分只是提前本来会发生的写入 |
| 4：清理待机缓存 | 丢弃已有干净缓存页 | 数据重新需要时可能要读盘，降低缓存命中 |

工作集包含当前驻留物理内存的可分页页面。裁剪后的页面可能仍在 RAM，不能把所有缺页都说成磁盘访问；脏的过渡页重新利用前需要写入后备存储。[微软 Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set)

命令名称、编号和结构来自内部 Native API 用法，不是具有公开稳定兼容承诺的 Win32 清理接口。phnt 原始声明将相关结构标为 `private`；本机成功不等于所有未来 Windows 版本兼容。[System Informer/phnt 原始声明](https://raw.githubusercontent.com/winsiderss/phnt/master/ntexapi.h)

## 最重要的策略问题：指标与动作错配

当前阈值计算是 `100 × (Total − Available) / Total`；默认自动动作却只清待机。微软明确 `Available = Standby + Free + Zero`，因此把待机转为空闲主要是可用池内部转换，通常不能直接降低这个触发指标，还可能损失缓存。这是根据当前代码与微软指标定义作出的推论，不是所有负载下的实测保证。[微软 MEMORYSTATUSEX](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/ns-sysinfoapi-memorystatusex)

现有保护包含默认关闭、85% 持续 60 秒、30 分钟冷却、5 个百分点迟滞、禁止并发、连续三次自动失败暂停。限制合理，但不解决指标和动作错配。不要简单把默认动作升级成更激进的全量整理作为“修复”。本次 UI 更新不擅自改变这些策略和用户选择。

## 本机证据与局限

独立评估读取当时的 19 条历史记录，均为三步且全部记录返回成功。即时可用内存增加约 0.58～5.88 GiB，中位数 2.92 GiB；耗时约 7.56～23.71 秒，中位数 10.77 秒。只公开匿名聚合，不公开原始用户记录。

这些观测证明调用返回成功且即时可用量发生变化，不能证明游戏帧率、任务耗时或操作流畅度改善。提交量变化方向不一致，其他程序活动也影响前后差值。没有清理后持续走势、磁盘增量和业务延迟，无法量化净收益；整理耗时也不等于整机卡顿时长。

## 硬件风险与普通清理比较

| 风险 | 评估 | 依据与限制 |
| --- | --- | --- |
| 直接 RAM/CPU 硬件损伤 | 低，未发现代码机制 | 没有调电压、频率或固件；不等于绝对保证 |
| 性能反作用 | 中；频繁全量整理或敏感负载更高 | 裁剪、刷脏页、丢缓存可能引起读写竞争和缺页 |
| SSD 累计写入 | 有潜在额外负担，大小未知 | 反复写回、读回、修改再写回可能增加写入；释放 3 GiB 不等于写盘 3 GiB |
| 系统兼容性 | 中 | 内部接口需按 Windows 版本验证，不支持时停止并解释 |

微软存储说明指出，合并重复写入能够减少闪存累计流量并延长寿命，读取的寿命影响小得多。该来源讨论服务器存储缓存，只用于支持闪存写入寿命原理，不直接证明本软件在消费级 SSD 上的磨损量。[微软存储缓存说明](https://learn.microsoft.com/en-us/windows-server/storage/storage-spaces/cache)

“普通内存清理”不是固定技术：若其他工具也调用相同三条命令，底层效果属于同类；只用公开 `EmptyWorkingSet` 裁剪选定进程时，当前全系统三步通常干预更广；正常关闭不需要的应用则会真正释放其拥有的资源，性质不同。公开接口也不保证提速。[微软 EmptyWorkingSet](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-emptyworkingset)

## 优化方向（建议，尚未实现）

1. **P0：先纠正策略目标。** 保持自动默认关闭，避免把高占用→清待机包装成压力解决方案；全三步应明确标注代价，而不是无限提升力度。
2. **P0：补收益证据。** 对同样工作负载比较不清理、各单步、三步组合，观察后续 1～5 分钟的可用量、提交量、硬缺页、磁盘读写与任务延迟。游戏关注帧时间尾部，不只平均 FPS。需用户另行授权测试，不在后台自动跑压力实验。
3. **P1：建立收益反馈。** 无收益或 I/O 明显恶化时延长冷却或暂停自动尝试，结合持续压力和用户活动，不只看百分比。
4. **P1：针对性与兼容性。** 评估公开接口、明确选择的后台进程与前台负载保护；内部命令管理已验证 Windows 版本，不支持时明确降级。不要任意终止其他应用。
5. **P2：诊断内存增长来源。** 增加提交压力、占用趋势及异常增长提示，帮助处理泄漏、不必要进程；相比反复清缓存，更可能带来持续收益。

日常建议：不要为看到更多“释放量”连续点击，也不建议开启短间隔全三步定时清理。正常的缓存占用并非浪费；需要更多持续可用空间时，优先正常关闭不用的程序、解决异常占用或评估扩容。
